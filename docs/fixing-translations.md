# 오역 고치기

틀린 번역 한 줄을 찾아 고치고, 다른 문장이 깨지지 않았는지 확인해서 올리는 방법입니다.
처음이면 [따라 해 보기](#따라-해-보기)부터 읽으세요. 무엇이 맞는 출력인지는 [번역 규칙](../spec/README.md)을 따릅니다.

## 준비

빌드 방법은 [build.md](build.md)에 있습니다. 운영체제마다 프리셋과 실행 파일 위치가 다릅니다.

| 운영체제 | 빌드 | 실행 파일 |
|---|---|---|
| Windows | `cmake --preset windows-x64` 후 `cmake --build --preset windows-x64` | `build\windows-x64\Release\hdtrans.exe` |
| macOS | `cmake --preset mac` 후 `cmake --build --preset mac` | `build/mac/hdtrans` |
| Linux | `cmake --preset linux` 후 `cmake --build --preset linux` | `build/linux/hdtrans` |

이 문서는 실행 파일을 `hdtrans`, 규칙 컴파일러(같은 폴더의 `hdrulec`)를 `hdrulec`, 프리셋을 `<preset>`으로 줄여 씁니다.
명령은 저장소 최상위 폴더에서 실행합니다.

사전을 고친 뒤 결과가 바로 보이게 하려면 사전 캐시를 끕니다. 캐시는 사용자마다 하나라서, 빌드 여러 개를 함께
돌릴 때 섞이지 않게 하는 데도 씁니다.

```sh
export HDTRANS_CACHE_DIR=off          # Windows PowerShell: $env:HDTRANS_CACHE_DIR = "off"
```

## 따라 해 보기

`競走で勝った。`가 "경주로 이겼다"로 나오는 오역을 예로 듭니다. "경주에서 이겼다"가 맞습니다.

**1. 누가 그 단어를 골랐는지 봅니다.**

```sh
echo 競走で勝った。 | hdtrans -dicts dicts -why
```

표준 오류로 단어마다 `WHY` 줄이 나옵니다. 볼 것은 표면형, 고른 번역, 끝의 층과 규칙입니다.

```
... で ... (으)로 ... defaults
```

`defaults`는 어떤 규칙도 이 단어를 고르지 않아 사전의 기본 후보가 쓰였다는 뜻입니다. 규칙이 골랐으면
`local L1276`처럼 규칙이 나옵니다(열 설명: [pipeline-layers.md](pipeline-layers.md#누가-정했는지--why)).

**2. 같은 단어의 다른 후보를 봅니다.**

```sh
grep -P '^で\t' dicts/base.tsv
```

`에서` 후보 행의 `rule` 열이 1276이면, 지역 규칙 L1276이 조건이 맞을 때 그 후보를 고릅니다. 그 행의
`ctx` 열이 조건이고, 읽어 보면 앞 명사가 경기(`VRw`) 뜻일 때만 `에서`를 고르게 되어 있습니다. 그런데
`grep -P '^競走\t' dicts/base.tsv`로 보면 競走에는 그 의미 코드가 없습니다.

**3. 고칩니다.** 규칙을 넓히는 대신 사전 행에 빠진 코드를 넣습니다. `dicts/base.tsv`의 競走 행 `sem` 열에 `VRw`를 적습니다.

**4. 테스트를 남깁니다.** 바뀌어야 하는 문장과 바뀌면 안 되는 문장을 함께 둡니다.
`tests/rules/cases/`의 표에 그 규칙을 이름한 사전 행의 id로 행을 더합니다:

```
dict:jisjk:114690  競走で勝った。  경주에서 이겼다.   fix   local
dict:jisjk:114690  力で勝る。     힘으로 우수하다.  keep  local
```

규칙을 사전에서 찾을 때는 번호 대신 그 규칙을 가리키는 행을 찾습니다:
`awk -F'\t' '$7==1276' dicts/*.tsv`.

**5. 확인합니다.** [다시 만들기와 테스트](#다시-만들기와-테스트)를 돌리고, 많은 문장에서 무엇이 바뀌었는지
[판정](#판정)으로 봅니다.

## 어디를 고칠까

| 증상 | 고칠 곳 | 예 |
|---|---|---|
| 기본 번역이 늘 틀림 | `dicts/base.tsv` 행의 `ko` | お仕置 `징계` → `벌` |
| 사전에 없는 말 | `dicts/words*.tsv`에 새 행 | 疼き `욱신거림` |
| 규칙이 그 단어를 못 알아봄 | 행의 `sem`, `gram` 코드 | 競走에 `VRw` |
| 문맥에 따라 뜻이 갈림 | `src/core/dict/builtin/senses.tsv`나 지역 규칙 | |
| 규칙이 틀린 후보를 고름 | 규칙 조건 | L1276을 경기 문맥으로 좁힘 |
| 고를 규칙이 없음 | 새 행과 새 지역 규칙 | 分の `몫의` 행과 L5093 |
| 어미가 틀림 | `base.tsv`의 어미 행(품사 `S5..`) | なければと `6야 한다고` |
| 그 문맥에서 후보를 빼야 함 | `src/core/word/constraints.cpp`의 `kRules` | なる 앞 こう |
| 인용, 연결이 틀리게 조립됨 | `src/core/word/`의 rewrites 패스 | たらと思う `-면 하고` |
| 의성어, 감탄사, 문형 | `builtin/sound.tsv`, `phrases.tsv`, `patterns.tsv` | |

같은 원인이면 데이터(사전 행과 코드)로 고칠 수 있을 때 데이터를, 안 될 때 규칙을, 그래도 안 될 때 엔진 코드를 고칩니다.
어느 층을 고칠지는 아래 [원인에서 고치기](#원인에서-고치기)로 먼저 정합니다.

- 기본 번역을 바꾸면 그 단어가 나오는 모든 문장이 바뀝니다. 다른 쓰임을 먼저 찾아 봅니다.
- 틀렸거나 애매한 번역만 고칩니다. 외래어를 소리대로 옮긴 것은 틀린 것으로 보지 않습니다.
- 꿀도르 같은 외부 사용자 사전은 `dicts/`에 합치지 않습니다([ehnd-compat.md](ehnd-compat.md)).

## 원인에서 고치기

가장 작은 변경은 원인을 없애는 가장 작은 변경입니다. 증상만 가리는 변경은 같은 원인의 다른 문장을 그대로 둡니다.

**1. 오류가 처음 생긴 단계를 찾습니다.** `-why`와 `--trace`로 정규화, 소리와 보호 구간(`sound`, `protect`), 분절, 형태 분석(품사,
활용), 후보 선택, 어미와 인용의 조립, 띄어쓰기 중 어디서 틀렸는지 봅니다. 층 이름과 순서는 [pipeline-layers.md](pipeline-layers.md)에
있습니다. 그 단계를 고칩니다. 앞 단계의 잘못을 뒤 단계에서 덮지 않습니다. 분절이나 분석이
틀린 것을 구 전체 행이나 출력 치환으로 가리지 않습니다.

**2. 고치기 전에 같은 원인을 셉니다.** 많은 문장(판정에 쓰는 문서, 줄 단위 회귀 문장, 참조 샘플)에서 같은 모양을
`tools/count-class.py`로 셉니다. 여러 단어에 걸치면(대략 서로 다른 단어 5개 이상이나 20줄 이상) 단어마다 행을 더하지 않고
그 원인을 고칩니다. 의미 코드, 코드와 부류를 보는 규칙, 엔진 코드가 그 자리입니다. 줄 수보다 단어 수가 중요합니다. 줄이 적어도
같은 모양의 단어가 여럿이고 한 장치로 모두 고쳐지면 그 장치를 고칩니다.

**3. 증상만 가리는 변경인지 따져 봅니다.**

- 조건이 예문의 표면형을 늘어놓고 있지 않은가.
- 같은 부류의 다른 동사나 명사로 바꿔도 맞는가.
- 같은 조건에 걸리는 다른 문장은 무엇이고, 그 문장에서도 맞는가.

하나라도 걸리면 한 층 더 내려가 원인을 고칩니다.

**4. 이럴 때는 엔진 코드를 고칩니다.**

- 데이터나 규칙으로 하면 비슷한 행을 많이 늘어놓아야 할 때
- 규칙이 판단에 필요한 정보를 볼 수 없을 때
- 뒤 단계가 앞 단계의 결정을 덮을 때
- 형태 분석 자체가 틀렸을 때

고친 단계 옆에 단위 테스트(`tests/unit`, `hdtest.h`)를 두고, 규칙 사례도 함께 남깁니다.

**5. 낱말 문제는 사전 행으로 고칩니다.** 빠진 말, 틀린 뜻풀이, 굳은 관용구는 행 하나가 원인 수정입니다.

**6. 커밋 메시지에 적습니다.** 원인 단계, 같은 원인을 가진 줄이나 단어의 수, 그 층을 고른 이유를 씁니다.

| 증상 | 증상만 가리는 변경 | 원인 수정 |
|---|---|---|
| そうはいきません → 그렇게는 살지 않습니다 | 문형마다 행 추가 | 가나 いき가 生きる의 긴 어간으로 분석되어 살다가 기본이었음. 두 동사가 같은 꼴은 가다, 앞말의 구문으로 되다, 없다를 고름 |
| 出て行った → 나와 갔다 | 복합어마다 행 추가 | 行く 복합어 151행이 く 동사 활용 부류에 있어 과거, て형이 맞지 않았음. 부류를 行く로 바꿈 |
| 呆然と, 凛と → 보연과, 늠과 | 낱말마다 `〜と` 행 추가 | タリ 형용사에 부류 코드를 붙이고 그 코드 뒤 と, として, たる를 고르는 규칙 |
| 王子と会った → 오지와 | 王子 지명 행 삭제 | 전역 규칙이 뒤 동사의 의미 계열만 보고 고유 명사 후보를 고르던 조건을 고침 |

## 사전 행 고치기

열 이름은 각 파일 머리줄에 있습니다. 코드의 뜻과 예는 [dictionary-codes.md](dictionary-codes.md)에 있습니다.

| 품사 | 뜻 | `ko` 쓰는 법 |
|---|---|---|
| `N110`, `N130` | 명사, 고유 명사 | 그대로 |
| `N311` | 부사 | 그대로 |
| `M4..` | 동사 어간 | 활용 표지로 끝남(`&AV@`는 하다) |
| `H7..` | い형용사 어간 | `$..@` |
| `G8U0` | 형용동사 | `%A1@` |
| `S5..` | 어미 | 활용형 숫자로 시작(`6야 한다고`) |
| `P2..` | 조사 | `(으)로` |

- 동사나 형용사는 같은 활용을 하는 기존 행을 찾아 활용 표지를 그대로 따라 씁니다. 넣은 뒤 했다, 해서, 하는처럼 여러 활용을 번역해 봅니다.
- `gram`의 `Hd`는 する가 붙는 명사, `Tu`는 앞말에 붙여 씀, `Ct`는 조수사입니다.
- 품사는 띄어쓰기에도 영향을 줍니다. 꾸미는 말이 뒤 명사와 붙어 나오면(몫의자리) 연체사 `E0H0`로 둡니다.
- 새 행에는 id가 있어야 사전을 불러옵니다. `words*.tsv`는 그 파일의 다음 `w:N`, `base.tsv`는 겹치지 않는 `이름:번호`를 씁니다.

## 규칙 고치기

- 지역 규칙의 본문은 그 규칙을 부르는 사전 행의 `ctx` 열에, 전역 규칙은 `src/core/rules/globals.txt`에 있습니다.
  `rule` 번호가 같은 행이 여럿이면 `ctx`도 모두 같아야 합니다.
- 무엇을 언제 고르는지 한 줄로 적습니다(지역 규칙은 `note` 열, 전역 규칙은 위 주석). 앞 규칙을 지우면 뒤 규칙이 대신 동작할 수 있습니다.
- 새 지역 규칙은 가장 큰 번호 다음 번호를 쓰고, 사전 행의 `rule` 열에 그 번호를, `ctx` 열에 본문을 적습니다.
- `&&N`, `||N`의 N은 그 묶음 안의 문장 수입니다. 대입(`D+0= "..."`)도 하나로 셉니다.
- 동사 어간은 `"L溢"`(그것으로 시작)처럼 비교합니다. `"R戦"`는 그것으로 끝남입니다.
- 규칙 언어 전체: [rule-language.md](rule-language.md), 컴파일러 진단: [rule-compiler.md](rule-compiler.md#사용법)

## 테스트 남기기

| 어디에 | 쓰는 경우 |
|---|---|
| `tests/rules/cases/<주제>.tsv` | 규칙의 결과. `expected`는 번역 전체, `rule:dict:<id>=<번역>`은 그 규칙이 고른 번역, `!rule:dict:<id>`는 그 규칙이 고르지 않아야 함. kind는 `fix`, `keep` |
| `examples/` | 문서 단위 결과. 출력이 바뀌면 `.ko.txt`를 고치되 첫 줄 주석은 그대로 |
| `tests/rules/drops/` | 낱말이 번역에서 사라지면 안 되는 입력(활용형 격자 등). ctest `rules.drops`(`tools/drops.py`)가 이 입력과 규칙 사례의 입력에서 한 글자씩 읽혀 번역이 빈 글자 두 개 이상을 찾고, `known-gaps.txt`의 입력만 봐줍니다. 측정 세트의 빠짐 수는 ctest `sets.drops`가 `tools/drops-budget.tsv`로 봅니다([testing.md](testing.md#낱말-빠짐-dropspy)) |

예문은 실제 글에서 짧게 발췌한 것(한 줄이나 그 일부)을 기본으로 합니다. 데이터에 없는 모양이나 조건 하나만 다른 짝이 필요할 때는 직접 지은 문장을 더하되, 사례의 대부분은 발췌입니다. 출처, 제목, 작품 이름은 적지 않고, 긴 대목을 통째로 옮기지 않습니다.

사례는 고친 예 하나가 아니라 그 유형 전체를 덮습니다. 데이터가 있으면 유형마다 15~30행을 두는데, 고친 모양마다 `fix`, 조건 바깥의 비슷한 문장마다 `keep`을 둡니다. 판정에서 나빠졌다고 나온 줄과 리뷰에서 돌려보낸 줄은 모두 올바른 출력과 함께 사례로 남깁니다.

## 다시 만들기와 테스트

규칙을 고쳤으면 생성 파일 두 개를 다시 만듭니다. 전역 규칙을 고쳤으면 먼저 빌드합니다.

```sh
hdtrans -dicts dicts --dump-rules build/rules.txt -in tests/empty.in   # 엔진이 조립한 규칙 프로그램
hdrulec lint build/rules.txt -dicts dicts                     # 마지막 줄이 0 error(s)
hdrulec dump build/rules.txt -hash > src/core/rules/program.hash
hdrulec cpp build/rules.txt -local 0-499 -globals -o src/core/rules/compiled_gen.cpp
```

빌드하고 전체 테스트를 돌립니다. 사전을 쓰는 테스트는 `HDTRANS_DICTS`가 있어야 돕니다.

```sh
cmake --build --preset <preset>
export HDTRANS_DICTS=$PWD/dicts      # PowerShell: $env:HDTRANS_DICTS = "$PWD\dicts"
ctest --preset <preset>
```

## 판정

`ctest`는 정해 둔 문장만 봅니다. 실제 글에서 무엇이 바뀌었는지는 기준 빌드와 비교해 바뀐 줄을 모두 판정합니다. 도구와
명령은 [testing.md](testing.md#변경-판정-e2e--모델-판정)에 있습니다.

- 고치기 전 커밋으로 따로 빌드한 것을 기준으로 삼습니다. 다른 사람이 계속 합치는 `develop`을 기준으로 쓰지 않습니다.
- 바뀐 줄은 `tools/measure.sh`가 줄 단위 회귀 문장, 참조 샘플, 테스트 데이터 문서, 웹 예제마다 판정 입력으로 씁니다.
  다른 챕터 폴더는 `tools/e2e-pairs.py`가 씁니다. 챕터는 고칠 때 본 챕터(개발 세트)와 보지 않은 챕터(held-out
  세트)를 따로 모으고 따로 보고합니다.
- 바뀐 줄은 표본을 뽑지 않고 모두 판정합니다. 판정자는 고친 사람이 아니고, 어느 쪽이 새 출력인지 모릅니다. 첫 판정(Sonnet)이
  모든 줄을, 둘째 판정(GPT, high)이 첫 판정이 나빠짐이나 같음이라고 한 줄을 다시 봅니다. 둘째 모델을 쓸 수 없으면
  블라인드 파일을 판정자 둘이 따로 보고, 답이 갈린 줄을 셋째 판정자가 봅니다(`tools/blind.py`). 줄이 많으면 판정 입력을
  나눠 판정을 동시에 돌립니다.
- 같은 주기에 합친 PR끼리의 상호작용은 합치기 전 rebase 뒤 다시 재고, 합친 뒤 마지막 릴리스와 비교해 봅니다
  ([주기 누적 확인](testing.md#주기-누적-확인-cycle)).
- 두 판정이 모두 나빠졌다고 한 줄이 있으면 고친 것을 되돌리거나 조건을 좁힙니다.
- 남기는 조건: 나아짐:나빠짐이 2:1 이상, 한 부류의 줄이 몰려 나빠지지 않음, 참조 샘플의 chrF가 기준보다 낮지 않음.
  개수와 두 판정이 모두 나빠졌다고 한 줄은 `tools/verdicts.py`가 셉니다.
- 본문, 번역, 판정 결과는 저장소 밖에만 둡니다.

## 올리기

- 번역이 바뀌는 수정은 따로 커밋하고, 무엇을 왜 바꿨는지와 판정 숫자(바뀐 줄, 나아짐, 같음, 나빠짐)를 적습니다. 판정에 쓴
  문서나 세트의 이름, 출처는 적지 않습니다.
- 규칙을 고친 커밋에는 `program.hash`와 `compiled_gen.cpp`가 함께 들어갑니다.
- 풀 리퀘스트는 `develop` 브랜치로 보냅니다. 커밋과 PR 제목은 `fix(rules): 조건 뒤 인용 수정`처럼 씁니다([제목 규칙](contributing.md#커밋과-pr-제목)).

## 여러 줄을 한꺼번에 고칠 때

```
측정 → 원인 추적 → 분류 → 고치기 → 확인 → 합치기 → 다시 측정
```

1. 측정: 모델이 줄마다 맞고 틀림, 틀린 부분, 고칠 말을 적은 판정 파일을 만듭니다(비공개 저장소).
2. 원인 추적: `tools/attribute.py`가 틀린 부분의 단어를 어느 층, 어느 규칙이 골랐는지 붙입니다.
3. 분류: 위 [어디를 고칠까](#어디를-고칠까) 표의 갈래로 나눕니다. 받아들일 만한 번역은 뺍니다.
4. 고치기: 갈래별로 브랜치를 나눠 동시에 고칩니다. 각자 자기 행과 자기 규칙의 테스트만 고칩니다.
5. 확인: 묶음마다 테스트와 판정을 한 번씩 합니다.
6. 합치기: 하나씩 합치며 생성 파일을 다시 만들고 테스트합니다. 다 합친 결과도 한 번 판정합니다.
7. 되돌린 수정은 원인별로 모아 다음 바퀴에 먼저 고칩니다. 코드 누락, 규칙이 보는 범위가 좁음, 뒤 단계가 앞 결정을 덮음이 흔합니다.
